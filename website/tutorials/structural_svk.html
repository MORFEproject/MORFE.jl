From a mesh to a ROM

Literate script — standardized walkthrough ↗

Two library calls turn a finite-element mesh into a nonlinear reduced-order model — and the same pipeline drives a Gmsh beam, a COMSOL arch and a CAD micromirror.

Runs today — current API

Every line on this page is the shipped implementation in examples/01_clamped_beam_ferrite. A smoke run takes seconds: MORFE_FAST=1 julia --project=. main.jl.

What this tutorial demonstrates

  • Going from a mesh file to a nonlinear reduced-order model in two library calls.
  • The case / pipeline split: everything problem-specific sits in one clearly marked block; the code below it never changes.
  • That the very same pipeline text drives three physically different structures — a Gmsh beam, a COMSOL arch, and a CAD micromirror.
  • Reading the reduced dynamics: eigenfrequency, backbone coefficient, and what the numbers mean.

The model

A geometrically nonlinear elastic structure discretised with St. Venant–Kirchhoff material obeys a second-order system on the free DOFs

$$\mathbf M \ddot{\mathbf u} + \mathbf C \dot{\mathbf u} + \mathbf K \mathbf u = \mathbf g(\mathbf u, \mathbf u) + \mathbf h(\mathbf u, \mathbf u, \mathbf u),$$

where $\mathbf g$ and $\mathbf h$ are the quadratic and cubic geometric-nonlinearity terms — the SVK strain energy produces exactly these two and nothing higher. DPIM computes a polynomial parametrisation $\mathbf u = \mathbf W(\mathbf z)$ of the invariant manifold tangent to a chosen mode pair, together with the reduced dynamics $\dot{\mathbf z} = \mathbf R(\mathbf z)$ on it. MORFEFerrite.StructuralSVK assembles $\mathbf K, \mathbf M, \mathbf C, \mathbf g, \mathbf h$ from the mesh and hands them to MORFE's solver.

01

State the case

The top of main.jl is a marked block holding everything that describes your problem. Adapting the example to a different structure means editing this block — nothing below it. 

# ── CASE — edit this block for your own problem ─────────────────
FAST = get(ENV, "MORFE_FAST", "0") == "1"

MESH      = joinpath(@__DIR__, "clamped_clamped_beam.msh")
MATERIAL  = SVK.SVKMaterial(E = 160e3, ν = 0.22, ρ = 2.32e-3)
DAMPING   = SVK.RayleighDamping(α = 5.4e-3, β = 1.9e-2)
DIRICHLET = "Dirichlet"   # facetset name in the mesh
MASTER    = [1]           # master conjugate mode pairs
ORDER     = FAST ? 3 : 9  # parametrisation order
FORCING   = nothing       # or SVK.HarmonicForcing(...)
Why a marked block, not a config file

For a dozen constants a separate file is ceremony. The knob-rich examples (parametric, Kármán) do use config.jl — the rule is one file when the case is small, two when it is not.

02

Assemble the mechanical model

One call reads the mesh, builds the FE space, applies the Dirichlet constraints, assembles $\mathbf K$ and $\mathbf M$ on the free DOFs, forms $\mathbf C = \alpha\mathbf M + \beta\mathbf K$, and prepares the SVK nonlinearity as a batched FEMMultilinearMap. 

model = SVK.mechanical_model(MESH;
    material = MATERIAL, damping = DAMPING, dirichlet = DIRICHLET,
    fe_order = FE_ORDER, quad_order = QUAD_ORDER)

The clamped–clamped beam of example 01 gives 4 977 free DOFs (40×3×1 hexahedra, quadratic Lagrange).

03

Compute the invariant manifold

The second call does everything else: solve the eigenproblem, select the master pair, build the resonance set, and solve the cohomological equations order by order. 

rom = SVK.parametrise(model; master = MASTER, order = ORDER, forcing = FORCING)

master = [1] selects the first conjugate pair, so the ROM has two coordinates $(z_1, \bar z_1)$. The solve is graded: coefficients of degree $N$ never depend on degrees above $N$, which is why the fast order-3 run is an exact truncation of the order-9 one — and why validate.jl can compare them directly.

Adding harmonic forcing

Setting FORCING = SVK.HarmonicForcing(mode = 1, amplitude = 0.03) appends two external states at $\pm i\Omega$ with the load shaped like the forced mode. Nothing else in the pipeline changes.

04

Read and save the result

SVK.print_equations(rom)
SVK.save_rom(rom, joinpath(@__DIR__, "results"))

save_rom writes the standard layout — data/W.jls, data/R.jls, data/R_coefficients.csv and a summary.txt carrying the Julia version, git commit and timestamp. For the beam the first rows read:

monomialcoefficient of $\dot z_1$meaning
(1,0)−0.0053741 + 0.53738515 ieigenvalue $\lambda_1$: damping + frequency
(2,1)−5.3752e−7 + 2.4472e−5 ileading backbone (hardening) term

Both numbers are asserted by the example's validate.jl against its blessed reference — every figure quoted on this page is checked by code.

Three cases, one pipeline

The pipeline text below the CASE block is character-for-character identical in the three structural examples (verified by diff). They differ only in what the case says:

01 · Clamped beam (Gmsh)
MESH = "clamped_clamped_beam.msh"
DIRICHLET = "Dirichlet"
ORDER = 9

4 977 DOFs · $\omega_1 = 0.5374$ rad/ms

03 · Polysilicon arch (COMSOL)
MESH = "arch_2_force.mphtxt"
DIRICHLET = Set([1, 11])
QUAD_ORDER = 4

3 429 DOFs · $\omega_1 = 1.0327$ rad/ms · P18 wedge mesh read straight from COMSOL, Dirichlet given as entity IDs

08 · MEMS micromirror (CAD)
MESH = "mirror_gimbal.msh"
# generated by mesh.jl from STEP

Torsional gimbal mode; the CAD → Gmsh step is one extra script, the ROM pipeline is unchanged

Recap

  • A structural ROM is mechanical_model then parametrise — two calls.
  • The case block is the only thing you edit; the pipeline is library code you re-use.
  • Mesh provenance (Gmsh, COMSOL, CAD) is a case detail, not a pipeline concern.
  • Graded solves make a fast low-order run a genuine truncation of the production run.
  • Every number in the docs is asserted by the example's validate.jl.
